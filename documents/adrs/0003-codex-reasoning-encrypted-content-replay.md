# ADR-0003: Replay OpenAI reasoning items via `encrypted_content` for Codex

## Status
Accepted

## Date
2026-07-12

## Context
Users reported that `codex:gpt-5.6-*` reasoning turns show only the bold
`**header**` in the UI with no detail text underneath — sometimes preceded by
a literal `<!-- -->` HTML-comment placeholder, sometimes (currently) nothing
at all after the header.

Investigation ruled out the frontend/markdown-rendering theory: the raw
`reasoning_content` string genuinely is just the header; there is no hidden
text being swallowed by comment-stripping in rendering. It also ruled out a
request-parameter bug unique to `gpt-5.6`, since every Codex model shares the
same `_CodexResponsesHandler`/`ResponsesHandler` code path and only
`gpt-5.6-*` shows the symptom.

Cloning `openai/codex` (the reference Codex CLI, Rust) and diffing its actual
request-construction logic against ours turned up one concrete, confirmed
mismatch: upstream unconditionally sends
`include: ["reasoning.encrypted_content"]` on every Responses API request
(`codex-rs/core/src/client.rs::build_responses_request`), and replays the
full `ResponseItem::Reasoning { id, summary, encrypted_content }` verbatim in
the next turn's `input` (`client_common.rs::get_formatted_input_for_request`
just clones the whole turn history, including `Reasoning` items). Our Codex
provider set `store: false` but never requested `encrypted_content` and never
replayed any reasoning item back into history at all — every multi-turn
tool-calling turn lost reasoning continuity that the reference client always
preserves. OpenAI's own guidance states this is required for `store: false` /
stateless workflows, and is most impactful exactly where the symptom
concentrates: tool-calling turns (`openai/codex#31664` reproduces the same
"header, no detail" symptom on `gpt-5.5` even with a fully spec-compliant
request, confirming the root generation gap is server-side and not fully
avoidable — but continuity still measurably helps model quality per OpenAI's
own cookbook benchmarks).

Note this is a **mitigation, not a fix**: `encrypted_content` is ciphertext
carrying the model's raw chain-of-thought for its own later recall. Only
OpenAI's servers can decrypt it, and it is architecturally unrelated to the
human-readable `summary` text that populates `reasoning_content` — verified
directly against a live `codex:gpt-5.6-terra` session after deploying this
change: `reasoning_encrypted_content` is populated (1100–1500+ chars) on
every reasoning turn, while `reasoning_content` still comes back as only the
header, with no second `summary_text` part at all. The detail text is simply
not being generated by the model/backend right now; there is nothing to
recover from the encrypted blob.

## Decision
Round-trip the OpenAI Responses API reasoning item exactly like the reference
Codex CLI does:

1. `_CodexResponsesHandler.build_request` always sends
   `include: ["reasoning.encrypted_content"]` (unconditional, matching
   `client.rs` — not gated by `store` or service tier).
2. `ResponsesHandler.parse_response` / `_parse_stream`
   (`app/agent/providers/openai/responses.py`) capture the completed
   `reasoning` item's `id` and `encrypted_content` off the response/stream.
3. `AssistantMessage` gains two new `exclude=True` fields:
   `reasoning_item_id` and `reasoning_encrypted_content`.
4. `ResponsesHandler.convert_messages` replays a
   `{"type": "reasoning", "id", "summary": [], "encrypted_content"}` item
   immediately ahead of its associated `function_call` item, matching
   upstream ordering, whenever an `AssistantMessage` carries a stored
   `reasoning_encrypted_content`.
5. Persistence reuses the existing generic `extra` round-trip mechanism
   already used for other provider-opaque data (e.g. Anthropic's
   `reasoning_signature`): `app/agent/agent_loop/streaming.py` writes both
   fields into `extra` and onto the assembled message;
   `app/services/chat_service_messages.py::deserialize_messages` restores
   them from `extra` on session reload.

This lives in the shared `ResponsesHandler` base class (not Codex-only) so
any other Responses API caller gets the same behavior for free — it is a
no-op when `encrypted_content` is absent from a response.

## Alternatives Considered

### Do nothing — accept it as a pure upstream/model bug
- Pros: no code change; matches the fact that OpenAI's own reference client
  shows the identical symptom with a fully correct request.
- Cons: leaves an easy, low-risk, documented-best-practice improvement on the
  table; other reasoning + tool-calling turns benefit from continuity
  regardless of whether it fixes this specific symptom.
- Rejected because: the gap versus the reference client was concrete and
  free to close, even though it doesn't guarantee eliminating the missing
  detail text.

### Persist and replay the plaintext `summary` only (skip `encrypted_content`)
- Pros: simpler, no opaque blob to store.
- Cons: does not restore actual reasoning continuity — `summary` is
  after-the-fact prose, not usable by the model to resume its own chain of
  thought. Contradicts OpenAI's documented mechanism, which is specifically
  `encrypted_content` for `store: false` continuity.
- Rejected because: it wouldn't address the underlying (partial) cause the
  investigation identified.

### Add a client-side reasoning-continuity mechanism instead of OpenAI's (e.g. re-summarizing prior turns into the prompt)
- Pros: avoids depending on an opaque, provider-specific blob.
- Cons: reinvents what `encrypted_content` already does natively, worse
  fidelity, extra tokens/latency.
- Rejected because: OpenAI provides this exact mechanism for this exact
  problem; use it rather than approximate it.

## Consequences
- `AssistantMessage`/`SessionMessage.extra` now carry two more optional
  fields (`reasoning_item_id`, `reasoning_encrypted_content`) for any
  Responses API provider that returns them — additive, no schema migration
  needed (stored in the existing JSON `extra` column).
- Codex (and any other Responses API caller using `include`) requests are
  slightly larger per turn (encrypted reasoning items replayed in history);
  bounded by however many reasoning-bearing turns are in context.
- Does **not** guarantee `gpt-5.6-*` (or any model) emits real reasoning
  detail text — that gap is confirmed server-side
  (`openai/codex#31664`) and outside this codebase's control. If OpenAI fixes
  it upstream, no further client change is needed to benefit.
- Verified live against a running dev session
  (`019f54eb-01b9-7197-b937-4ff7b5c89156`, `codex:gpt-5.6-terra`):
  `reasoning_encrypted_content` populates correctly turn over turn;
  `reasoning_content` remains header-only, confirming the mitigation works
  and the remaining symptom is upstream.
