# The app: other computers and remote control

Part of the [feature catalogue](../features.md), under *1. The desktop coding workspace*. The index explains the version tags.

- **Switch Server from the command palette** `[v3.32.0]` — run **Switch Server…** in the
  command palette (⌘K) to list the builtin sidecar and saved servers (current one
  marked, online/offline shown) and connect with Enter. It reuses the Settings →
  Server checks (reachable, access key accepted); a failure shows a toast and
  keeps the current server. No keyboard shortcut; desktop app only.
  Since `[v3.34.0]`, picking a server here or in Settings → Server covers
  the window with **Switching to *name*…** right away (it fades in after a
  beat, so an instant switch never flashes it), and the startup screen keeps
  the same words through the reload until the new server is up. A failed
  connect closes it and shows the error where you started.
  Since `[v3.57.0]`, the screen has **Back** (top left on a phone; Escape and
  Android Back too): it calls the switch off at once, with no error, and you
  are back where you picked the server, free to pick another. Back goes away
  only for the last moment, once the switch is committing. A computer of your
  account that opens after Back is dropped and the app stays on the server
  it was on. The startup screen's "Switching to …" after the reload has Back
  too: it goes back to the server you came from (on a phone, your Computers).
- **Lighter over a remote connection** `[v3.46.0]` — a running reply reaches
  the phone app (or any browser on another machine) in about a third as many
  stream updates and roughly 60% fewer bytes; the first words still appear
  at once and text stays in order. Reopening a session that has not changed
  downloads nothing (the server answers "not modified"), and on the phone
  app the file list and git status revalidate the same way. Coming back to
  the phone app while the agent works fetches only what was saved while it
  was in the background, and tool cards that finished meanwhile show as
  done at once. History pages no longer carry the provider-internal replay
  data (raw content blocks, thinking signatures, reasoning items) that made
  up close to half of their bytes. A tool's output (a file read, a command's
  output, search results) no longer comes with the session: it loads when
  you open the tool row or copy its result, and a running command still
  shows its output live. Tool rows no longer show a result summary (line or
  match counts, test totals) or a red failure mark; cards built from their
  answer (questions, plans, goals) look as before, and a patch's line
  numbers and diagnostics, a todo or schedule list, and a preview's page
  outline load when you open the row. Opening a tool row in a long session
  answers in under a millisecond on the server. A
  reopened session also leaves out a described command's text, a patch's
  diff and a plan's text: the row still shows the description, the files
  with their line counts and the plan action, and the rest loads when you
  open the row. Opening a session with subagents no longer downloads their
  latest messages (the main view never shows them; opening a subagent loads
  its own conversation), and images you attached or the agent showed are
  not downloaded again when you reopen a session. Each saved message also
  leaves out the fields the app never reads (stop reason, cost breakdown,
  undo bookkeeping), about a fifth of what is left of a long session.
  A running reply reaches a phone or another computer compressed, at about
  a ninth of the bytes, with each update still arriving at once.
- **Update a computer's desktop app from another device** `[v3.54.0]` — the
  same **Update to vX** now works when the server is the desktop app on a
  Mac or a Windows PC, which is the usual case for a phone. One tap, and the
  app on that computer downloads the release, verifies its signature,
  installs it and restarts; a notification on the computer says so first.
  Running sessions resume, and the device that asked reconnects on its own
  and says how it went. The button is also under the row of the server in
  use, on the phone's Servers screen and in the desktop's Server dialog. The
  tap can only start the app's own updater: it installs the latest signed
  release from the app's feed, never a chosen file or an older version. On
  Windows the installer may wait for someone at the computer, and the note
  says so. A Linux app is a `.deb`, which nothing can replace from afar: it
  says to update the app on that computer. In the desktop app on its own
  built-in server the row points to the app's **Updates** section, which
  updates both. The app's install dialog now says that running agents resume
  after the restart (they always did).
- **LAN access key for external clients** `[v1.43.0, v1.103.0, v2.4.0]` — `agentd server start --host 0.0.0.0 --key`
  stores the CLI server's bind address, port, and bearer key in `server.yaml`, separate from the desktop builtin sidecar's ephemeral token while agents, providers, sessions, and other settings remain shared. Restart and upgrade preserve that key without exposing it in process arguments. OpenAgentd-managed launchers refuse non-loopback binds without a configured key `[v1.101.0]`.
- **Desktop server connection manager** `[v1.43.4, v1.99.8, v1.104.0]` — the desktop **Server connection** dialog switches the current window between the builtin sidecar and saved external servers, normalizes pasted `/api` URLs, and preserves other open windows' backend choices. Typed servers now require a successful health and access-key test before they can be named, saved, and connected. Saved LAN access keys are scoped per backend origin and stored in the native OS credential store on mobile; browser development keeps the per-origin localStorage fallback. Remembered external servers reconnect on app launch with sidecar fallback, while the desktop window opens immediately as backend startup continues asynchronously `[v1.57.1]`. Since `[v3.29.0]` the desktop app never connects to a saved server on its own: launch always starts the builtin backend, and saved servers are listed with Online/Offline and Connect, joining only the window where you click Connect (the next launch is back on builtin). The mobile app, which has no builtin backend, still reconnects to its last server.
  - **Add and edit in place** `[v3.40.0]` — Settings → Server opens no form by itself: **Add a server**, at the end of the list, opens the form for a new one (Test, then **Save and use**). Each saved server has **Edit**, which opens its form right under its row; **Save** updates it there without switching to it (a new address or access key needs a passing Test first, a rename does not). Escape or **Cancel** closes the form and puts focus back on the button that opened it. A scanned connect link still opens the add form filled in.
  The desktop keeps them in `access-keys.json`, a file only your user can read, in its app config folder, instead of the OS credential store `[v3.22.0]`: macOS ties a keychain item to the signing Team ID of the app that saved it, which the unsigned desktop app does not have, so it asked for keychain access after every update. Keys saved in the keychain by earlier versions are not carried over; enter them again in the Server dialog.
  - **Reload after switching backend servers** `[v1.98.1]` — after connecting a desktop window to a different saved or typed external server, the webview reloads so stale frontend state is discarded and the window comes back against the newly selected backend cleanly. Reconnecting to the already active backend does not reload.
- **Desktop network access** `[v3.15.0]` — a **Network access** switch in desktop **Settings → Server → Access from other devices** (and the **Server** dialog) lets phones and other computers on the LAN connect to the builtin backend without installing the CLI. When it is on, the builtin sidecar also listens on `0.0.0.0:4082`. If 4082 is taken, it uses the next free port and the dialog says so. The port goes back to 4082 once it is free again. Every client needs the access key except `/api/health/*`. The desktop generates the key, keeps it in a file only your user can read (`network-access-key` in its app config folder; before v3.22.0 it was in the OS credential store, so devices paired earlier need the new key), and can show, copy, regenerate, or replace it with your own (16+ characters). The listener turns on and off live, with no backend restart and without stopping running turns. Turning it off or changing the key immediately disconnects devices using the old key, including open event streams and terminals. The setting is re-applied whenever the builtin backend restarts, and network access ends when the app quits. Traffic is plain HTTP. The Windows installer adds a firewall rule for the builtin backend on Private networks only, so there is no admin prompt; on a network marked Public the port stays closed. When devices cannot connect, the dialog shows a per-platform firewall hint: the Private network profile on Windows, a `ufw`/`firewall-cmd` command on Linux, and the firewall setting on macOS. `[v3.16.0]` While network access is on, **Show QR** displays a code with the LAN addresses and the access key. Scanning it with a phone camera opens the OpenAgentd mobile app's **Server** dialog with the first reachable address and the key filled in, and tests the connection; the phone connects only after you tap **Save and use**. The code hides when the key changes or network access turns off.
  `[v3.46.0]` The code carries the OpenAgentd seal in its centre and uses a higher error-correction level, so it still scans.
  `[v3.49.0]` The iOS and Android apps scan it themselves: **Scan QR code** under Settings → Server (beside **Add a server**) opens the camera (asked once) and fills in the same form; a code that is not a connect code, or a camera that is off, says so.
- **Remote control (beta, optional)** `[v3.50.0]` (named OpenAgentd Cloud until `[v3.57.0]`) — reach your computers from your iPhone away from home, and get notified when agents finish. Nothing changes for people who don't sign in: local use, LAN pairing and `agentd server start --public --key --qr` work as before, and no screen asks for an account. It is offered only in a skippable card on the phone's Servers screen and in **Settings → Account** (desktop and phone); `agentd cloud join | login | status | logout` does the same on a headless server, and `agentd server status` adds a `Cloud:` line once signed in.
  - **A new iPhone or iPad: scan it with your phone** `[v3.57.0]`. A new iPhone or iPad with no account opens on **Use your computers on this iPad**: a QR code and "Open OpenAgentd on your iPhone and tap Scan." On the old phone, **Scan** on Computers shows **Add this iPhone or iPad?** ("It can use your computers."; its device ID, uses and **Can add devices** are under **Details**), then Face ID, then **Tap this number on the iPhone or iPad** with a 2-digit number; the new device asks **Which number is on your iPhone?** among three, and lands on Computers with "You're all set. Your computers are below." A wrong number, Cancel or two minutes leave the account and erase its keys. The code renews by itself when it times out; with no network the screen says so and offers **Try again**. **No iPhone nearby? Sign in with Google** (the sign-in code, and the same device ID the account page shows) and **Lost your phone? Use your recovery code** are links under the code; **Other ways to connect** shows the usual Computers screen (connect codes, computers by address, invitations). A phone added this way can add devices, as before. The phone's Account no longer offers scanning or pasting an invitation under its own menu *(deprecated)*: Computers → **Scan QR code** still takes one.
  - **Remote control, in plain words** `[v3.57.0]`. The feature is called **Remote control** (Settings → Remote control, on the desktop and the phone); "your OpenAgentd account" is still what you sign in to. One wording on every screen: **Can add devices** (never approve or signer), **Device ID** (never key or fingerprint), "This code timed out. Show a new one." for every expired code, "Not added. Try again on the device you're adding." when codes don't match, and "This iPhone can't add devices. Use the phone you set up first." The command is `agentd remote login | join | approve | recover | status | logout`; `agentd cloud …` still works as a hidden alias.
  - **Adding a device: QR invitation first.** On the phone, **Settings → Account → Add a device** shows a QR code for 10 minutes, and only while that screen is open (closing it or leaving the app cancels it). Another phone scans it; a computer can't scan, so **Can't scan? Use a link** shows the same invitation as a link, after a warning that it works like a password. Paste it in the computer's **Settings → Account**, or run `agentd cloud join` (it asks for the link without echoing it). The phone then shows the new device's kind and fingerprint, which the new device shows too, and adds it only when you tap **Add** (Face ID). If two devices claim the same invitation, nobody is added, the invitation is cancelled, and the phone offers a new one. The 6-digit code stays as the fallback: **Use a 6-digit code instead** on the phone, **Sign in with a code instead** on the computer, or `agentd cloud login`. An account holds up to 10 devices.
  - **Scan to add a computer** `[v3.55.0]`. In the desktop app, **Settings → Account → Sign in** shows a QR code next to the browser way; `agentd cloud login` draws it in the terminal. On an iPhone that approves devices, **Servers → Scan QR code** opens **Add this computer?**. Adding needs Face ID and shows a two-digit number: choose it on the computer (or type it in the terminal) to join. A wrong number, Cancel or no answer makes the computer leave again; it connects only after the right number. The browser way remains for a first device or when no phone can approve. The phone's Add a device sheet no longer offers a copied invitation link *(deprecated)*; a desktop can still show one. The scanner now reads sign-in codes, invitations and server connect codes.
  - **Connect your phone in one click** `[v3.56.0]`. In the desktop app, a phone button in the status bar (and **Connect Your Phone** in the command palette) signs this computer in with server and client on and shows the QR code at once; it is there only on the app's own server, until the computer is in an account. The sign-in screen shows just the QR code: the browser way folds under **Can't use your phone? Sign in in the browser**, and the roles move under **Options** (on the guest card and on the phone's **Add this computer?**, which defaults to what the computer asked for). An iPhone that is not signed in yet can scan a computer's code too: it signs in (creating the account if needed) and then opens **Add this computer?** without a second scan; Android says adding a computer needs the iPhone app for now. On a server, `agentd server start --cloud` starts it and then signs in as `agentd cloud login` does, and a plain `server start` suggests `agentd cloud login` to a person not signed in.
  - **The phone sets up the account.** Signing in on the phone shows a recovery code once (you type two of its groups back); other devices join an account the phone approves, by invitation or by comparing a 6-digit code on both screens and confirming with Face ID or the passcode. Since `[v3.51.0]` any device can be first (below); use `agentd cloud login` on a computer. The old `--first-device` flag is no longer needed or accepted *(deprecated)*.
  - **Any device signs in first; servers and clients** `[v3.51.0]`. A computer creates the account from **Settings → Account → Sign in** or `agentd cloud login` (it asks before creating one, then shows the recovery code). Signing in chooses what the device is for: **Use as server** (your other devices open sessions on it) and **Use as client** (it opens sessions on your other computers); a computer offers both, on by default in the app, while `agentd cloud login` is server-only unless given `--client`; a phone is a client only. A later device signs in the same way and waits; every device that approves gets "A device wants to join your account" (a push on the phone, which opens the request when tapped; a notification and an in-app prompt in the desktop app; `agentd cloud approve` on a headless computer). Approving compares the 6-digit code on both screens and confirms with Face ID, Touch ID or the login password; the approver can turn a requested role off but never add one. Each device's roles show in **Devices**. A server-only device cannot open sessions on others, and a client-only computer runs no relay connector. On a computer, only a person approves or removes devices: in the desktop app (which proves the confirmation to its own server), or with `agentd cloud approve` typed in a terminal; an agent's commands, a script, or a plain browser tab cannot, and say where to do it instead.
  - **End-to-end encrypted.** Traffic between the phone and a computer goes through the relay inside a Noise session keyed to the account's signed device list, which every device verifies; the relay cannot read it, and the cloud cannot add a device. On the computer, relayed requests are served in-process, never as a local caller, and lose any credential or proxy header the phone sends. Done / Needs you / Failed notifications are sealed to the phone and opened by its notification extension.
  - **One row per computer.** The phone's Servers list shows each account computer once, with the way it is reached: **On your network** or **Through your account** (since v3.53.0; before, "via LAN" when its saved LAN address answered). Saved servers keep their own rows.
  - **Phone account without a server** `[v3.51.1]`. The Account section sits at the top of the phone's Servers screen before any server has answered, so a new phone can sign in, join or approve first and then open a computer. Below it, **Your computers** lists the account's computers (titled by their own names since v3.54.0, never by a saved server's name); the account's bridge never shows as a stray `127.0.0.1` server, and a phone with no computer yet says how to add one.
  - **Online and In use** `[v3.51.1]`. Each computer has a dot from the account (online, offline, or none when the account cannot say) that refreshes every 30 seconds while the screen is up; an offline computer can still be tapped. **In use** marks the computer the app is on, by either route.
  - **A tap always connects or says why** `[v3.51.1]`. A tap on an account computer opens it directly on the home network when it can, else through the account (since v3.53.0; before, over its saved LAN address when that answered). A saved server whose address stopped answering is not In use, and a tap opens it again; at launch, a saved server that does not answer shows the Servers screen as before.
  - **Scan one QR code** `[v3.51.1]`. The phone has one **Scan QR code** button, in the Account card and under Your servers, for both kinds of code: an account invitation joins the account (the Account sheet shows Joining, then the Servers screen lists your computers), a server's connect code fills the add-server form, and anything else gets one message that names both. **Paste link** stays in the Account sheet.
  - **The desktop shows an invitation** `[v3.51.1]`. **Settings → Account → Add a device** in the desktop app shows a QR invitation for 10 minutes, with the same rules as the phone's: it ends when you close the sheet, when it expires or when the server stops; the new device's kind and fingerprint show on both screens, and it is added only after **Add** and Touch ID. If two devices claim it, nobody is added. Only the desktop app can start one: relayed requests, agent tools, scripts and plain browser tabs cannot.
  - **Copy the recovery code** `[v3.51.1]`. The recovery step has **Copy code** and says to keep the code in a password manager; the copied code is cleared from the clipboard after two minutes.
  - **A computer's relay connection recovers by itself** `[v3.51.1]`. A computer gives up a relay connection that has not answered for 60 seconds, or at once after waking from sleep, and reconnects; **Settings → Account** says online only once the connection is really open. It also sends a small keepalive the relay can see, so phones can show a sleeping computer as offline once the relay supports it; with an older relay it falls back to how it worked before.
  - **A quiet chat stays connected away from home** `[v3.51.2]`. A session opened from the phone through the relay no longer drops and reconnects every minute or two while nothing is happening: both ends send the relay's keepalive on the session too, and with an older relay they fall back after one reconnect. A connection that really died is still noticed within about a minute. After a drop the chat reattaches once, not twice, and the computer's server log says why each phone session ended (`cloud_session_ended`).
  - **Joining and staying connected are more reliable** `[v3.51.3]`. A join that fails, times out or is cancelled (closing the sheet, Ctrl-C in `agentd cloud login`) withdraws its request, so a few abandoned joins no longer block new ones for 10 minutes. Waiting for the sign-in code rides out rate limits, server errors and network blips until the code expires. A refused sign-in or join says why: too many requests (and how long to wait), 3 devices already waiting to join, an account with 10 devices, a device already in the account, an account scheduled for deletion or unavailable, or no connection. Phone sessions on a computer stay open when its relay connection drops for a moment or is renewed after 24 hours; only removing the computer or a locked account ends them. Two copies of a computer with the same account keys no longer take the connection from each other every second: the one taken over says so and tries again every few minutes. A used-up daily relay allowance shows as paused at once, and connecting never sits on "Connecting" for more than about 30 seconds.
  - **Pushes survive a network blip** `[v3.52.0]`. A Done, Needs you or Failed push the computer could not send (no network, the cloud busy) is retried for up to 10 minutes, and a newer one for the same session replaces it. Tapping a push opens its session on the computer that sent it (see Native app notifications). When the phone opens the same computer twice at once (a tap while it reconnects), both share one connection instead of the second cutting off the first.
  - **Faster and steadier through your account** `[v3.53.0]`. A request through the relay no longer waits 50 ms on each end before it is sent (small writes now leave after 2 ms, with the same long-run message rate), so a small request takes about one round trip to the relay and back, not two plus 100 ms. Each device reuses its relay token for its 15 minutes instead of asking for one per connection, and failed retries no longer use up its token allowance. Each computer keeps one connection that reconnects by itself (from 0.5 s, backing off to 30 s), checks itself within 3 seconds when the app comes back to the front or the network changes, and stops trying in the background; a request waits at most 10 seconds for it before the "Can't reach … · Retrying…" banner shows. A relaunch returns to the computer last opened. A large transfer no longer holds up a small request in the same session, and a computer that slept is noticed as soon as it wakes.
  - **Stays connected after the phone was locked** `[v3.53.1]`. The phone app reaches its account computer again when it comes back from the background: iOS may take a suspended app's local connection to the computer without saying so, so the app stops it in the background and opens it again in front (on the same address and with the same key, so the page needs no reload), and checks it whenever a retry is asked. A failed open no longer cuts off the computer the app is on, a reload no longer leaves the connection waiting for the app to come back, and a large reply that overlapped another request no longer ends the session on 3.53.0 hosts and phones. The last row of the phone's Servers screen, **Copy diagnostics**, copies what the app saw of its connections (the last 50 events, with the app version and time; no keys, tokens or addresses) for a problem report.
  - **Open your other computers from the desktop app** `[v3.53.0]`. On a computer signed in to an account (with **Use as client**, the default), Settings → Server lists **Your computers**: every other computer of the account that serves sessions, with Online or Offline (refreshed every 30 s while the list shows), the one in use marked, and **Use** to open it in that window. ⌘K → Switch Server… lists them too, between the built-in server and the saved ones. The built-in server holds the account keys, so it keeps the connection to each opened computer (the same self-healing link as the phone) and closes it once no window uses it; with the built-in server stopped the list says so and offers **Start**, and a computer signed in without **Use as client** says it cannot open others. Account calls always go to this computer's own server, so Settings → Account keeps working while a window shows another computer. The footer, the health dot and the notch name the computer in use, and one computer saved under two addresses (or opened through the account too) shows its sessions once in the notch.
  - **Direct at home, through your account away** `[v3.53.0]`. On the same home network, the phone and the desktop app reach a computer of your account directly, with the account's device keys: nothing to type and no access key. Leave home and the same chat keeps going through your account within seconds, with no reload; come home and it moves back by itself. The computer's row says which way it is reached: **On your network** or **Through your account**. The computer tells your devices where to find it only inside an encrypted session, so the cloud never learns its addresses, and a device tries them only on the network where it learned them. A computer accepts direct sessions only from devices of the account that may open sessions, on its private addresses, and refuses a device that was removed or left the account (also after a restart without internet); a computer that hasn't heard from the cloud for 7 days stops accepting them until it does. It's on by default for a computer used as a server, with a switch in **Settings → Server → Let your account's devices connect directly on this network**. Saved servers (an address with an access key, **Allow devices on your network to connect**) are a separate thing and work as before; a machine that is both shows two rows, and an account computer never takes a saved server's name (it has its own, see below). Each computer keeps one local address in the app across launches, so its page storage stays.
  - **Names for your computers** `[v3.54.0]`. Each computer has a name: its own host name ("studio-mini") until you call it something else ("Work", "Personal"). Your computers, the Devices list, ⌘K → Switch Server…, the status bar, the phone's header, the tray and the notch show that name where they showed a system and key ("macOS · 3F9A 21C4") or an address. The name lives on the computer and an app reads it over the connection it already has, so every device of yours shows the same one after its next connection. `[v3.56.0]` Your account keeps the names too (see **One name per device** below), so the cloud stores each device's name; before, it never saw them. **Details** on a row (⋯ or a long press on touch) holds what the row no longer carries: the system, the key, the role, and for the built-in server its address; a saved server's address is in its **Edit** form. **Rename** is in the Details of every computer of your account (Your computers and the Devices list, on a phone or in the desktop app), and of the built-in server in the desktop app; an empty name gives the host name back. `[v3.55.0]` Any device of the account may rename any of its computers, approver or not: a computer you are not on is renamed through its link in the background, and the app stays where it is. A computer that predates names says to update it. A row is a name and one status line; a computer the app has never been on, and a phone (which has no name), are still titled by system and key, and the key joins a name only while two computers share it. A saved server is titled by the name you gave it, else by its computer's name, else by its address. A name is at most 40 characters of plain text and is only a label: nothing trusts a device by it, and removing a device still asks with its system and key in full. An older server reports no name and keeps its old title.
  - **One name per device, kept by your account** `[v3.56.0]`. Each device has one name, stored with your account, and every device and list shows that same name, also before the app has reached the computer. Renaming in **Details** changes it everywhere (a device renames itself; a device that approves new devices renames any of them); a computer keeps its own server name and its account name in step, whichever changed last, and a computer that joins names itself after its host name. The names your app remembered for your computers before this update go to your account once, where it has none yet. A phone has no name of its own (iOS gives apps none): it shows as **This phone**, or by the name you give it. A name is at most 40 characters of plain text and is still only a label.
  - **Signed-out devices leave the list** `[v3.56.0]`. A device that signed out disappears from every device list at once instead of staying as a row that can't be used; a computer that approves removes it from the account's signed device list in the background, and the phone does so with its next approve, add or remove. Signing out on the only device that approves new devices warns first, as removing it does.
  - **Lost your phone? Use your recovery code** `[v3.56.0]`. When the device that approves new devices is gone, **Settings → Account → Other ways to sign in → Lost your phone?** (on a computer and on a phone, also from the waiting sign-in steps) takes the recovery code saved when the account was set up, then a sign-in in the browser. That device then approves new devices and every other device is signed out, to sign in again from it. The recovery code stays the same afterwards, and the screen says so. On a server, `agentd cloud recover` does the same. A wrong code says so and changes nothing.
  - **Only one device can approve** `[v3.56.0]`. While a single device approves new devices, the Account screen says so above the list, with a button that lets another device (your phone, or a computer with a screen first) approve too; any device's **Details** has **Let it approve new devices**. On the phone it asks for Face ID.
  - **A simpler Account screen** `[v3.56.0]`. Signed out, the screen is one sentence and **Sign in**; the invitation link and the recovery code fold under **Other ways to sign in**, and sign-in asks no roles (a computer is a server and a client; `agentd cloud login` keeps its role options). Signed in, it is one list of your devices by name, this one first with **Sign out**; the status, key, roles and sharing that were a separate panel are in each device's **Details**. The phone's Servers screen shows a single **Sign in** row to a phone that isn't signed in.
  - **Keys stay on the device:** the iPhone keeps them in the Keychain (the approval key behind Face ID); computers keep them in `cloud/identity.json` in the server's state folder, readable only by your user. Signing out leaves the account and erases the keys; sessions and settings stay. Removed, deleted, closing and unavailable accounts each say so; in every state the app keeps working on its own, and only reaching other devices through the relay and notifications stop.
  - **Face ID before every device change** `[v3.56.0]`. On the iPhone, approving, adding or removing a device asks for Face ID (before, Face ID iPhones only ever asked for the passcode), with Touch ID or the passcode as the fallback. Cancelling changes nothing, and you can tap again to retry. An iPhone without a passcode is told to set one before it signs in, instead of failing after the recovery code.
  - Not yet: Android, changing a device's roles after it joined. Approving from a computer arrived in `[v3.51.0]`. The protocol is in `appv3/contract/tunnel.md`, its threat model in `appv3/contract/tunnel-threats.md`.
